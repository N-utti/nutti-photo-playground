# 07. 결정 로그 (ADR-lite) · 결정 카드 · 스펙 정오표

> 기준: wireframe-spec v0.5 / cebb865

## 1. ADR-lite — 확정 결정

각 결정은 이번 문서 세트(01~06) 작성 과정에서 확정되어 이미 스키마·API·아키텍처에 반영된 것들입니다. 배경·선택·근거·영향·기각 대안 순으로 기록합니다.

### ADR-01 · 크레딧 원장을 append-only + dedupe_key로 설계

- **배경**: 크레딧이 무상 배포로 바뀌면서(v0.2→v0.3) 결제 대신 다경로 지급(주문/연동/팔로우/매일)이 생겼고, 각 경로가 중복 지급되면 어뷰징이 된다.
- **선택**: `credit_ledger`를 append-only 원장으로 두고 `dedupe_key TEXT NOT NULL` + `UNIQUE(member_id, dedupe_key)`로 멱등성을 보장(`guest_trial`/`link_account`/`follow_ig`/`daily:<date>`/`order:<order_id>`/`clawback:<order_id>`/`job:<uuid>`/`refund:<uuid>`).
- **근거**: W-10 B "받은 내역" 화면이 원장 조회 그 자체라 별도 이력 테이블이 불필요하고, 배치 재실행·중복 탭 같은 재시도 상황에서 UNIQUE 제약 하나로 중복 지급이 원천 차단된다.
- **영향**: `04-erd.md` §2.8, 크레딧 트랜잭션 4단계 절차(락→검사→INSERT→UPDATE) 전체가 이 설계에 의존.
- **기각 대안**: 잔액 컬럼만 UPDATE — 이력 표시 요구가 나오는 순간 별도 이력 테이블을 다시 만들어야 해 결국 원장과 같은 구조에 도달. 무효.

### ADR-02 · 음수 잔액 허용(클램프 폐기)

- **배경**: 주문 보상 후 취소(Q3) 시 회수를 어떻게 처리할지 — 잔액을 0으로 클램프하면 "받은 크레딧을 다 쓴 뒤 취소"한 사용자를 회수할 방법이 없다.
- **선택**: 회수는 전액 그대로 차감해 잔액이 음수가 되어도 허용. 표시는 `max(0, balance)`, 차감 판정은 `balance >= cost`.
- **근거**: 음수 상태에서는 새 생성 시도가 항상 거부되므로, 다음 지급(매일 무료 등)이 자동으로 음수를 상환할 때까지 사용자가 서비스를 이용할 수 없다 — "보상 받고 취소" 반복 어뷰징이 클램프 로직 없이 구조적으로 차단된다.
- **영향**: `04-erd.md` §3.3, `member.credit_balance`에 하한 CHECK 없음.
- **기각 대안**: 0 클램프 + 추가 지급 보류 플래그(draft v1 초안) — 플래그 상태를 별도로 추적해야 해 원장 역분개보다 복잡하고, 정상 취소 고객까지 플래그로 발이 묶일 위험. 무효.

### ADR-03 · 게스트를 별도 테이블로 두지 않고 `member.kind`로 통합

- **배경**: 비로그인 사용자도 무료 체험·업로드·생성을 하므로 게스트 자산(pet/source_image/job)이 로그인 시 회원에게 이관돼야 한다.
- **선택**: `member.kind = 'guest' | 'member'` 단일 테이블. 로그인 시 기존 회원 행이 있으면 자산을 이관하고 게스트 행에 `merged_into_id`를 기록(병합), 없으면 게스트 행 자체를 `member`로 승격.
- **근거**: 별도 테이블이면 승격/병합 시 job·result·ledger 소유권을 전부 이관해야 하는데, 같은 행이면 이관이 0건(신규 가입)이거나 몇 개 FK UPDATE(병합)로 끝난다.
- **영향**: `04-erd.md` §2.1, `03-usecases.md` UC-07, `05-api-spec.md` §4 시나리오1.
- **기각 대안**: 게스트 전용 테이블 분리 — 승격 시 소유권 이관 비용만 발생하고 얻는 것이 없어 무효.

### ADR-04 · 생성 상태 전달은 HTTP 폴링(SSE 아님)

- **배경**: W-05가 "창을 닫아도 됩니다"를 명시적으로 약속 — 연결 유지가 요구사항이 아니다.
- **선택**: `GET /v1/jobs/{id}`를 2초 간격 지수 백오프로 폴링. `eta_seconds`/`progress`는 서버가 큐 길이 기반으로 계산.
- **근거**: SSE는 모바일 백그라운드 전환·프록시에서 끊기고 끊김 처리 코드가 결국 폴링으로 수렴한다. 20~40초 작업에 2초 폴링은 요청 10~20회 수준이라 이 규모에서 서버 비용이 아니다.
- **영향**: `05-api-spec.md` §4 시나리오2, `03-usecases.md` §3 상태머신.
- **기각 대안**: SSE — 대기 시간이 크게 늘거나 동시 사용자가 많아지면 재검토, 그 전까지는 도입하지 않음.

### ADR-05 · 작업 큐는 Postgres `FOR UPDATE SKIP LOCKED`(Redis/arq 미도입)

- **배경**: 생성 작업이 비동기 큐를 필요로 하지만, 동시 처리량은 초기 규모에서 수십 건 수준으로 추정.
- **선택**: 별도 큐 시스템 없이 `generation_job` 테이블 자체를 `FOR UPDATE SKIP LOCKED`로 폴링. 코드베이스에서 raw SQL을 쓰는 유일한 지점으로 한정.
- **근거**: 1인 운영 전제에서 Redis는 "관리할 컴포넌트 하나 추가"에 불과. arq 승격 임계(재처리율 1%↑ 1주 지속 / 폴링 지연 P95 10초↑ / 워커 스케일 아웃 필요) 3건 중 1건이라도 충족 시 검토.
- **영향**: `06-architecture-deployment.md` §2.
- **기각 대안**: 처음부터 arq/Redis 도입 — 지금 필요 없는 확장성을 지금 관리 부담으로 맞바꾸는 셈이라 기각(YAGNI).

### ADR-06 · 배포는 국내 단일 VPS + Docker Compose + Cloudflare R2/CDN

- **배경**: 트래픽은 SNS 유입 기반 스파이크형, 운영 인력 1인, 비용은 광고비 예산.
- **선택**: VPS(A) + R2/CDN(공통 정규화)을 추천안으로 채택.
- **근거**: 이그레스 손익분기 계산(월 3,000job 가정 시 이그레스 비용 ~$1.19/월, 결정 요인 아님) 이후에도 **구성 요소 수 최소화(1인 운영) + 국내 레이턴시**가 실질적 차별 요인으로 남음. C(PaaS)는 해외 리전 실시간 상호작용(업로드·폴링) 지연이 약점.
- **영향**: `06-architecture-deployment.md` §5. 결정 대기 2건(클라우드 계정 유무, 월 예산 상한)은 §2 결정 카드로 이관하지 않고 06 문서에 남김(스키마 영향 없는 순수 인프라 결정이므로).
- **기각 대안**: B(AWS 풀스택) — 1인 운영에 과한 관리 복잡도. C(PaaS) — 실시간 상호작용 지연.

### ADR-07 · 카페24 연동은 폴링(웹훅 아님)

- **배경**: 주문 보상(+20)이 카페24 주문 데이터에 의존하는데, 웹훅은 유실 시 감지가 어렵다.
- **선택**: 배치가 `last_synced_at`(워터마크) 기준으로 신규 주문을 주기적으로 조회.
- **근거**: 웹훅 유실이 곧 "조용한 지급 중단"으로 이어지는데, 폴링은 유실이 있어도 다음 주기에 자연히 회복된다(워터마크가 진행점을 기억).
- **영향**: `06-architecture-deployment.md` §6.2.
- **기각 대안**: 웹훅 수신 — 유실 감지·재처리 로직을 별도로 만들어야 해 폴링보다 복잡도가 높음.

### ADR-08 · `05-api-spec.md`를 2층 구조(§1·§2·§4·§5 장수명 / §3 소모성)로 설계

- **배경**: 손으로 쓴 API 명세는 구현이 시작되는 순간 실제 코드와 어긋나기 시작한다.
- **선택**: §1(공통규약)·§2(화면-API매핑)·§4(시나리오)는 장수명으로 유지, §3(엔드포인트 스키마)는 **구현 착수 시 삭제하고 FastAPI 자동 생성 `/docs`로 대체**. §5(관리자 API)는 §1·§2·§4와 함께 장수명 유지 — 관리자 콘솔은 W-11 화면 계약이라 화면-API 매핑과 같은 수명. **삭제 전제조건(이슈 #4 반영)**: 전 엔드포인트에 `response_model` 부착 + `/openapi.json`에 응답 스키마 실노출 이후에만 — 그 전에 지우면 응답 계약이 어디에도 남지 않는다.
- **근거**: 화면-API 매핑과 시나리오는 "설계 의도"라 코드가 바뀌어도 유효하지만, 엔드포인트 스키마는 코드와 실시간으로 갈라지는 소모품이다. 손으로 쓴 `openapi.yaml`은 만들지 않음(원칙과 동일한 이유).
- **영향**: `05-api-spec.md` §0.
- **기각 대안**: 손으로 쓴 OpenAPI 전체를 장수명 계약으로 유지 — 아무도 갱신하지 않아 곧 거짓말이 됨.

### ADR-09 · 카페24 주문 동기화의 워터마크와 컷오프를 별개 컬럼으로 분리

- **배경**: "배치가 어디까지 조회했는가"(진행점)와 "이 회원이 언제부터 보상 자격이 있는가"(자격 필터)를 하나의 값으로 섞으면, 토큰 만료 복구 시 소급 조회가 막히거나 반대로 연동 이전 과거 주문에 부정 보상이 나갈 수 있다.
- **선택**: `cafe24_oauth_token.last_synced_at`(워터마크, 배치 진행점)과 `member.order_reward_cutoff`(컷오프, 회원별 연동 시점)를 별개 컬럼으로 분리.
- **근거**: 배치는 워터마크 이후 전체 주문을 조회하되, 지급 여부는 각 주문의 `member_id`에 연결된 컷오프와 비교해 최종 결정 — 두 관심사가 섞이지 않는다.
- **영향**: `04-erd.md` §2.1, §2.11, `06-architecture-deployment.md` §6.2.
- **기각 대안**: 단일 "마지막 처리 시점" 컬럼 하나로 두 역할 겸용 — 토큰 만료 복구 시 소급 조회 범위와 보상 자격 범위가 뒤섞여 위 두 사고(누락/부정지급) 중 하나가 반드시 발생.

### ADR-10 · AI 이미지 생성 프로바이더는 OpenAI GPT Image API

- **배경**: `06-architecture-deployment.md` §3이 Gemini 2.5 Flash Image / GPT Image 1.5·mini / Flux Kontext 3안을 비교하고 파일럿 후 확정을 권고했다.
- **선택**: **OpenAI GPT Image API**로 확정(2026-08-03, PO 결정).
- **근거**: PO의 운영 선호(OpenAI API 연동 사용 의사). 단가는 mini 티어 기준 3안 중 최저가 가능(§3 비교표), 단종 리스크(Gemini Nano Banana 2026-10-02) 회피.
- **영향**: `06-architecture-deployment.md` §3(확정 표기)·§7(`OPENAI_API_KEY`). 동기 응답형이므로 §3의 재시도 추적 절차(요청 발행 전 `attempt_count`·`status` 선커밋)가 적용됨. 파일럿의 목적은 프로바이더 선정이 아니라 **티어(1.5 vs mini)·품질 옵션 확정**으로 축소.
- **기각 대안**: Gemini 2.5 Flash Image(단종 예정), Flux Kontext(정체성 보존 우수하나 PO 선호 아님·입력 이미지 과금). 비교표의 품질 리스크(얼굴 세부 변형 사례)는 파일럿 실측으로 검증하며, 미달 시 `model_config.provider` 필드로 교체 여지 유지.

### ADR-11 · 로그인은 카카오·네이버·로컬 3종, 카페24는 로그인 후 "연동"으로 분리

- **배경**: 기존 설계는 카페24 OAuth가 사실상 유일한 정식 로그인이고 카카오는 보조(Q8)였다. 쇼핑몰 계정이 없는 신규 방문자에게 카페24 로그인은 가입 장벽이며, 프론트 이슈 #10에서 카카오 토큰 획득 경로 부재도 드러났다.
- **선택**: (2026-08-04, PO 결정) **로그인 수단 = 카카오 · 네이버 · 로컬(이메일+비밀번호) 3종**. UC-07 게스트 병합·승격은 이 3종의 가입/로그인 시점에 발생. **카페24는 회원의 쇼핑몰 계정 연동**(마이페이지 신설·W-10 크레딧 받기)으로 이동 — +3 크레딧과 `order_reward_cutoff`(주문 보상 자격)는 연동 시점 귀속 유지. 소셜은 **서버 리다이렉트(A안, 이슈 #10)** — 카페24와 동일한 authorize/callback 구조. `authorize`는 302 대신 **200 `{authorize_url}`** 반환(state가 토큰 주체에 바인딩되어 Authorization 헤더 필수 — 링크 이동으로는 헤더를 못 실음).
- **근거**: 가입 장벽 제거 + "+3 크레딧" 보너스로 카페24 연동을 유도하는 퍼널이 전환에 유리. 서버 리다이렉트는 키 미노출·프론트 배선 최소(프론트도 A안 선호).
- **영향**: `05-api-spec.md` §1 코드표·§2 W-06/W-10·§3 인증 전면·§4 시나리오 1/1-B, `04-erd.md` §2.1(`email`·`password_hash`·`naver_id`), `03-usecases.md` UC-07(로그인 주체 서술 — 후속 정리), 기존 카페24 콜백 구현(PR #8)은 "연동" 의미로 재작성 필요(다음 구현 PR). `PATCH/DELETE /v1/pets`는 마이페이지 소유(이슈 #9).
- **기각 대안**: B안 클라이언트 SDK(JS 키 2종 노출·도메인 등록 부담), 카페24 로그인 유지(가입 장벽), state 바인딩 완화로 302 유지(PR #8 C1 보안수정 후퇴).

## 3. 스펙 정오표 (errata)

와이어프레임 HTML(`docs/wireframe-spec-v0.5.html`)은 SSOT이며 **수정하지 않습니다**. 내부 모순이 발견되면 여기에 기록하고 채택값을 명시합니다.

이 규칙은 **기존 플레이트의 모순 수정**에 대한 것이고, **신규 플레이트 추가는 허용**입니다(이슈 #12 PO 해석, 2026-08-04). 추가 시 아래 표에 한 줄을 남깁니다.
